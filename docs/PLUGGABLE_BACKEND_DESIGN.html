核心结论

三轮代码探查证实：你的代码「状态层」和「渲染层」本就是分开的——规划器读的是 grid 数据结构，画面走的是另一条路，executor 刻意不碰渲染。所以这不是「硬撬解耦」，而是把已经存在的缝隙正式化成两个抽象接口：SimBackend（仿真后端）和 Renderer（渲染器）。MiniGrid 不再是「碰不得的遗留物」，而是和 Pygame 平起平坐的一个后端实现——可以为了对齐协议而重构它。新场景的全部需求（语义房间 / 家具 / 多彩 agent）都能映射到现有谓词系统，因此唯一不可动的硬约束只剩一条：规划内核 core/btp（改名自 mrbtp）零改动。

02 设计目标与铁律

把你这句话拆成可验证的约束。

你的要求设计落点

Demo 使用 与 底层渲染分开两条解耦缝：SimBackend 抽象 + Renderer 抽象
以后再加渲染要方便渲染器是协议（duck-typed Protocol），新增一个文件即插即用，零侵入
✓

唯一硬约束：core/btp 规划内核零改动——这是真正的价值边界，与动不动 MiniGrid 无关。两条工程原则：① 后端之间完全对称（MiniGrid / Pygame / 未来后端都只是「实现了 SimBackend 协议的一个类」，没有谁是特殊的）；② 加新后端 / 新渲染 = 新增文件 + 必要的薄重构，不牵动规划内核与执行循环。

⟳

相比上一版的关键变化：上一版为了「MiniGrid 一字不改」，让它当「被薄包装的遗留物（碰不得）」，而 Pygame 是「干净的一等后端」——这是不对称的。你松开这条约束后，MiniGrid 可以被重构进协议，于是所有后端对称平等，架构更干净。代价仅是：现有 MiniGrid demo 的入口/内部可能有薄调整（但行为不变，仍可独立验收）。

03 核心架构：两条解耦缝

一句话——仿真后端负责「世界长什么样 + 怎么变」，渲染器负责「怎么画出来」，两者通过协议解耦，Demo 编排层只依赖抽象。

规划内核 · 唯一不可动 后端层（含 MiniGrid 重构归位 + 新增 Pygame） 渲染层（含 MiniGrid 归位 + 新增 Pygame） 未来扩展点

为什么是「两条缝」而不是一条？

因为你的需求里藏着两件不同的事：

  • 缝 ①（后端）解决「世界能不能长成家庭/战场的样子」——MiniGrid 的房间是关卡写死的、物体类型有限，做不出「室内外 + 任意家具」。Pygame 后端给你一张自由画布：房间随便切、物体随便放。
  • 缝 ②（渲染）解决「同一个世界怎么画」——pygame 实时窗口、matplotlib 静态图、无头跑批，互不影响。这条缝让「以后再加渲染很方便」成立。
★

关键：后端和渲染正交。Pygame 后端可以配 Headless 渲染器在服务器上跑批；也可以配 Matplotlib 出论文截图。你远程开发的痛点（无显示器）由此自然化解——后端照跑，渲染换成出图即可。

04 接口契约：Pygame 后端要实现什么

这是规划器实际访问的全部接口（逐文件逐行盘点所得）。Pygame 后端只要实现这套鸭子接口，规划器一行都不用改就能在它上面跑。

(A) 后端 env 必须提供

方法 / 属性用途被谁用
grid（含 .get(x,y)/.set/.width/.height）世界格子，A* 寻路与碰撞多个 Action 节点
agents: list / num_agent智能体集合executor / 节点
obj_list / id2obj / obj_name2id物体注册表（按 id 查物体）Condition / 规划
room_cells / cells_room房间↔格子双向映射Go/Put 动作
get_room_index(pos) → int坐标属于哪个房间（语义核心）IsInRoom 等
doors_to_adj_rooms / adj_rooms_to_doors门连接哪两间房跨房移动
door_key_map / key_door_map门锁与钥匙配对CanOpen
set_focus_agent / get_focus_agent / agent_step(action)执行一步、改世界状态executor 主循环
create_action_model() / get_initial_state()构建动作模型与初始符号状态planner
check_conflict(premise) / step_count / verbose / blackboard / cache冲突检测、计步、缓存规划搜索

(B) agent 必须提供

接口用途

接口用途

动作原语沿用 minigrid 的离散模型（left/right/forward/pickup/drop/toggle/done）。Pygame 后端复用同一枚举即可——这样 Action 节点（PickUp/Toggle/GoTo…）一行都不改。这是「规划内核零改动」的前提，也是决策点 D1。

05 关键洞察：新需求 → 现有谓词的映射

你担心的「厨房 / 家具 / 不同 agent」会不会要改规划器？答案是不会。它们全都能映射到现有抽象。

你想要的映射到现有抽象规划器是否要改
厨房 / 客厅 / 卧室 / 室外花园就是 room（room_cells），只是数量更多、加一张语义别名表 {0:"厨房",1:"客厅"}否（仍用 IsInRoom）
把杯子放到沙发旁边IsNear(cup, sofa) + PutNearInRoom，沙发当锚点否（谓词已存在）
桌子 / 冰箱 / 掩体（装饰或锚点）WorldObj 子类，给个 type/color；不可拿的当墙或锚点否（只是数据）
agent 不同颜色 / 大小 / 形状agent 加 render_style={color,size,shape}，只有渲染器读它否（规划器不看外观）
占领据点 / 集结据点 = room → IsInRoom；集结 = IsNear否
开冰箱 / 坐沙发（真交互）要新谓词 IsOpen(fridge) + 新动作是（内核改动，建议二期）
✓

除了「让 agent 真的去操作家具」（开冰箱、坐沙发）需要加谓词，其余全部是后端 + 渲染层的活，规划内核纹丝不动。第一版把家具定位成装饰 + 锚点，避开内核改动。

06 场景一 · 家庭服务

室内（厨房 / 客厅 / 卧室 / 卫生间）+ 室外（花园 / 车库），中间用门连通。服务机器人把物品在房间之间搬运、归位。

要素设计
房间（room）厨房 / 客厅 / 卧室 / 卫生间 / 室外花园，共 5 区；语义别名表挂在场景里，规划器内部仍是 room-0..4
可拿物体杯子 / 遥控器 / 药瓶 等（ball-like，有 color/id），可被 PickUp / PutInRoom / PutNearInRoom
家具（锚点/装饰）冰箱 / 沙发 / 床 / 电视 / 灶台；第一版不可交互，作 IsNear 锚点或视觉装饰
门房间之间、室内↔室外用门连接，可带锁（复用 key_door_map）
机器人3 台不同外观（蓝圆 / 粉方 / 橙三角），体现「不同大小形状颜色」——仅渲染层区分
示例目标IsInRoom(cup, room-1) ∧ IsNear(cup, sofa)：把厨房的杯子送到客厅沙发旁

07 场景二 · 战场

开阔地形 + 掩体（墙/障碍）+ 据点（区域）。不同兵种协同占领据点、集结、运送补给。复用同一套谓词，换一身皮。

要素设计 / 谓词复用
地形区域蓝方基地 / 红方基地 / 中央据点（room-0/1/2），用 IsInRoom 表达「占领」
掩体 / 障碍不可踩的 wall-like 物体，影响 A* 寻路（天然支持，can_overlap()=False）
可运送物旗帜 / 弹药箱 / 补给箱（ball-like），用 PickUp + PutInRoom 表达「夺旗/送补给」
兵种（agent）侦察(圆) / 突击(方) / 支援(三角)，外观区分，规划上是同质 agent（一期）
示例目标IsInRoom(flag, room-0) ∧ IsNear(agent集结)：把中央旗帜夺回蓝方基地并集结
★

两个场景共用一套引擎。家庭 vs 战场的差别，全在场景数据（房间布局 / 物体清单 / 外观皮肤）和渲染主题（暖色家居 vs 冷色军事）。后端代码、规划器、谓词三者完全共享——这正是分层架构的红利。

编排层怎么用这两个抽象（伪代码）

from backends import make_backend, make_renderer
from scenes.home_service import home_scene

# 1) 选后端（minigrid 不变；pygame 新增），后端读场景数据建世界
backend = make_backend("pygame", scene=home_scene)
# 2) 选渲染器，正交组合：远程就用 save_frame/headless
renderer = make_renderer("pygame", theme="home", mode="save_gif")

# 3) 规划 + 执行：planner / executor 完全照旧，只认抽象接口
plan = plan_behavior_trees(backend, home_scene, optimal=True)
execute(backend, plan, on_step=lambda rec, env: renderer.render(env))
✓

plan_behavior_trees 和 execute 的签名没变——它们本来就只通过鸭子接口访问 env。换后端 = 换传进去的对象，换渲染 = 换 on_step 里调的渲染器。这就是「Demo 使用与底层渲染分开」。

D1 · 动作模型沿用 minigrid 的离散原语吗？
沿用 left/right/forward/pickup/drop/toggle/done（朝向 + 单步移动）→ Action 节点零改动；或改成连续/八向移动 → 要改 Action 节点与寻路。
✓ 已确认：沿用离散原语。这是「规划内核零改动」的前提，移动模型以后单独议。
D2 · 第一版家具是「装饰/锚点」还是「可交互」？
装饰/锚点（开冰箱不算"打开"，只作 IsNear 锚点）→ 内核不动；可交互（真的开冰箱、坐沙发）→ 要加新谓词 + 新动作，是内核改动。
✓ 已确认：一期做装饰/锚点，避开内核改动；真交互留作二期专门立项。
D3 · 渲染默认走哪种模式？
你是远程 Mac、无显示器，pygame 实时窗口要转发 X11/SDL 比较折腾；存帧出 PNG/GIF 则无显示器也能跑。
✓ 已确认：默认 save_gif/save_frame（远程友好），本地有屏时再开实时窗口，Headless 给 CI。
D4 · 新场景的「房间」用什么几何？
矩形房间 + 门（贴近现有 room_cells 模型，get_room_index 实现简单）；或任意多边形分区（更自由但 room 判定复杂）。
✓ 已确认：矩形房间 + 门。能表达家庭/战场全部需求，且与现有谓词无缝对接。
D5 · 两场景的多兵种/多角色，规划上要异质吗？
同质 agent（只有外观不同，能力一样）→ 复用现有任务分配；异质（侦察只能看、突击才能拿）→ 要给 agent 加能力约束，影响规划。
✓ 已确认：一期同质（外观区分即可），异质能力作为进阶留作后续。

11 风险与对策

风险对策
接口契约盘点有遗漏，规划器在 pygame 后端上跑挂P0 先把现有 env 重构进 MiniGridBackend 并跑通现有 demo，相当于用真实 env 反向校验契约完整；P1 再照此实现 pygame 后端
planner 的 flaky（goal 是 set + PYTHONHASHSEED）在新后端重现这是规划器固有特性，与后端无关；沿用现有「多 seed 重试」策略，新场景示例也内置重试
pygame 在远程无显示器环境报错用 SDL_VIDEODRIVER=dummy + 离屏 Surface 出帧；默认走 save_gif，不开窗口
A* 寻路在新地图（掩体多）上找不到路掩体用 can_overlap()=False，寻路天然绕开；地图设计时保证连通性，加单测校验
重构 MiniGrid 归位时意外改变其行为重构只做「对齐协议」的薄调整，不改物理/规划逻辑；P0 验收项就是「旧 demo 输出与重构前一致」（保留一份重构前的基准运行结果做回归对照）

12 一页纸总结

这个方案为什么成立

① 解耦缝本来就有——executor 不碰渲染、状态提取与画面分离，我们只是把它正式化成 SimBackend 和 Renderer 两个协议。
② 规划内核零改动——新需求（语义房间/家具/多彩 agent）全部映射到现有谓词 IsInRoom/IsNear，规划器看不到外观。这是唯一的硬约束。
③ MiniGrid 平等归位——它被重构成「实现 SimBackend 协议的一个后端」，与 Pygame 完全对称，没有谁是特殊的遗留物；P0 验收是它行为与重构前一致。
④ 未来扩展只加文件——新后端进 backends/（一个自包含文件夹）、新场景进 scenes/、新配色进 themes/。
⑤ 两场景共用一套引擎——家庭 vs 战场只是数据 + 皮肤的差别。
