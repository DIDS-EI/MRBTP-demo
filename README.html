Macro View · 宏观总览

四个角色，一条主轴

给若干机器人一个符号化目标（例如「把一个球搬进隔壁房间」），规划器把它回链成「每个机器人一棵行为树」，执行器在共享 2-D 栅格世界里逐拍运行，并可选地让机器人共享一块信念空间来彼此协调。整个系统由四个职责清晰的角色组成——读懂它们各自管什么、彼此怎么搭话，就读懂了整个 demo。

关键设计哲学：编排层（app/）与规划内核（core/）只通过 core/interfaces.py 里的两个 Protocol 对话。想换仿真器？实现 SimBackend 即可，规划器一行不改。想换画面？实现 Renderer 即可，执行器一行不改。仿真后端与渲染器是两条正交的轴。

Interface · 接口协议

可插拔的两条正交轴

core/interfaces.py 是整个项目的架构枢纽。它定义两个 typing.Protocol（结构化鸭子类型，无需继承）和一套工厂/注册表，把「算什么」和「长什么样」彻底解耦。

协议回答的问题关键方法现有实现
SimBackend「世界怎么动？」reset() · step() · get_initial_state() · create_action_model()backends/minigrid
Renderer「世界怎么画？」render(env, …) · 帧捕获 / 窗口刷新backends/pygame（窗口/GIF/无头）

注册表与工厂

# core/interfaces.py 暴露的「接缝」API
register_backend(name, factory)   # 把一个后端工厂登记到全局表
make_backend(name, scene, ...)    # 按名字造一个 SimBackend
make_renderer(name, ...)          # 按名字造一个 Renderer

minigrid 后端是惰性注册的——首次 make_backend("minigrid") 时才导入重依赖。

模块间的依赖与调用关系

🔌 教学层不碰 core 内部

examples / projects 只调用 app 的公开函数。这正是 demo 的承诺——用户面向入口是 app / examples，core 是引擎不直接用。

📦 状态靠数据类传递

app 四文件通过明确的数据类（Scenario / PlanResult / ExecutionResult）传状态，而非共享可变全局。

⚓ 唯一接缝在 interfaces.py

所有「造世界 / 造渲染器」都走工厂，规划/执行代码只依赖协议而非具体实现——换后端/换画面零侵入。

🔍 scenes 自动发现

pkgutil.iter_modules 扫描 scenes/，导出 NAME+make() 即注册为场景；下划线模块跳过。加场景 = 丢一个数据文件。

Run · 安装与运行

装上就能跑

# 安装
cd mrbtp-demo
python3 -m venv .venv && source .venv/bin/activate
pip install -e .            # 装 app + 精简 core + 依赖；注册 mrbtp-demo / mrbtp-verify

# 完整 warehouse 场景，4 机器人，带窗口
python -m app.run

# 快速无头冒烟（开门 + 搬一个球，2 机器人）
python -m app.run --smoke --renderer none

# 自建两张专属地图，用 pygame 增强渲染器
python -m app.run --scenario home   --renderer pygame
python -m app.run --scenario battle --renderer pygame

# 分工规划：一机器人一个子目标（仅最优规划器）
python -m app.run --scenario battle --single-expand

# 无头自检 + 自动重试
python -m app.verify          # 或：mrbtp-verify

4 个开箱即用场景：warehouse / smoke 是经典两房 DoorKey；home / battle 跑在自建专属地图上。规划/执行旋钮（--planner / --no-composite / --single-expand / --share-belief）正交，对每个场景都生效。

⚠️

执行是随机的：GoBtwRoom 每次重规划会重排路径，两个机器人偶尔在门口死锁，所以单次冒烟约 70% 成功，设种子也压不住。这正是 verify.py 默认重试 5 次的原因。

Trimmed vs Upstream · 精简对照

相对上游 mrbtp 砍掉了什么

移除项原因
envs/virtualhome/（~470 KB）三维家居仿真器；本 demo 只用 MiniGrid。一行死的 import UnityCommunication 曾把它整个拖进来——那行已删。
envs/numerical_env/符号化基准环境，MiniGrid 链路从不加载。
envs/gridenv/minigrid_computation_env/纯计算的栅格变体，此处未用。
llm_client/LLM 驱动宏的 OpenAI 客户端；本 demo 用预定义宏。
~12 个重型 pip 依赖openai/hydra-core/sympy/matplotlib/opencv/networkx 等——精简后的代码都不 import。
🔑

剩下的 mrbtp 规划算法（MABTP / MAOBTP / 回链 / 复合动作）是与上游逐字节一致的代码——只删了未用子包和一行死 import。整个仓库约 750 KB。
