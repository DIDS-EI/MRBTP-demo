app · 多机器人行为树规划全流程详解

把单体脚本 main.py 拆成三段式、重注释的可读流水线： 一个符号化目标 → 每个机器人一棵行为树 → 在 MiniGrid 里执行并可视化。 本教程图文并茂地讲清架构、模块关系、数据流，以及如何扩展你自己的案例。

📦 6 个模块 · ~1100 行 🧠 规划 MAOBTP / MABTP 🌍 MiniGrid DoorKey 🤝 共享信念空间开关 🔧 mrbtp 库 · 算法零改动

01概览 · 它是什么

MRBTP = Multi-Robot Behavior Tree Planning（多机器人行为树规划）。给定一个所有机器人需要 共同满足的符号目标（例如"把 0 号球搬进 1 号房间"），系统会为每个机器人各自 规划出一棵行为树，让它们在网格世界里协同把任务完成。

app 这个包并不是新算法——它原封不动复用底层的 mrbtp 库（规划器、行为节点、环境的算法逻辑都没动），只是把原来挤在一个文件里的"演示胶水代码" 拆成了职责清晰的几块。这样你读代码时，可以一段一段地理解整条流水线。

PART 1 规划

把符号目标反向回链成每个机器人一棵可执行的行为树。

PART 2 执行

每一步驱动所有行为树，把动作落到网格上，带信念共享开关。

PART 3 可视化

渲染 MiniGrid 窗口 + 打印每一步行为树 tick 结果。

💡 一句话类比

把它想成给一队搬运机器人写"剧本"：scenario 定义舞台和剧情目标，planner 是编剧把目标 拆成每个演员的台词剧本（行为树），executor 是导演喊"开始"让大家同步表演，visualize 是把舞台投到屏幕上。

06行为树（Behavior Tree）是什么

行为树是机器人/游戏 AI 里常用的决策结构。它是一棵树，每一步（tick）从根节点往下遍历， 每个节点返回 SUCCESS / RUNNING / FAILURE，由控制节点决定接下来走哪个分支。

🔀 控制节点

Selector（选择/?）：从左到右尝试子节点，有一个成功就成功——"实现目标的多种办法，挑一个能用的"。
Sequence（顺序/→）：从左到右执行，必须全部成功——"按步骤一步步来"。

🍃 叶子节点

Condition（条件）：检查世界状态，如 IsInRoom(ball-0,room-1)。
Action（动作）：实际去做事，如 PickUp / GoBtwRoom，执行中返回 RUNNING。

MRBTP 的规划器做的事，就是从目标条件出发反向回链：要让 IsInRoom(ball-0,room-1) 成立，需要先 PutInRoom，而那又需要先 PickUp 和 GoBtwRoom……一层层倒推， 最终长成下面这样一棵可执行的树：

🧩 复合宏（Composite Action）

像 GetKeyAndOpenDoor、Move0BetweenRooms 这种"多步子任务"，在 scenario 里用一串 原子动作预定义好（见 §扩展）。规划时它们被当成一个 0 成本的整体动作塞进搜索空间， 让规划器可以"一步"选中整段子任务——这就是论文里 LLM 风格宏的思想。

07共享信念空间 · 这个 demo 的灵魂开关

多机器人最难的是协同：两个机器人怎么知道"门已经有人去开了，我不用重复去"？答案是 executor.execute(share_belief=...) 这个开关控制的共享信念空间 （blackboard 上的 predict_condition）。

实现上有个巧妙之处——关闭共享时不改任何库文件：executor 在运行时把每个 agent 实例上的 finish_current_task / update_current_task 两个方法替换成"不广播"版本 （用 types.MethodType），并清空预测集合。行为树节点读到的预测条件永远为空，于是只能根据真实环境状态决策。

❷ planner.py — Part 1 规划 ●

核心函数 plan_behavior_trees(env, scenario) 三步走，产出 PlanResult：

1
建动作模型 — env.create_action_model() 列出每个机器人能做的所有原子动作。
2
预规划复合宏（可选）— CompositeActionPlanner 把宏库展开成子树，作为 0 成本动作塞进搜索空间。
3
多机器人回链搜索 — MAOBTP（成本最优，支持宏）或 MABTP（FIFO 基线）把目标反推成每机器人一棵行为树。
⚠️ 注意

MABTP（optimal=False）不支持复合宏，此时会自动忽略宏库、只用原子动作，并打印一条黄色提示。

❸ executor.py — Part 2 执行 ●

execute(env, plan, share_belief=True, max_steps=500, on_step=...) 是主循环。它每一步： ① 让每个 agent tick 自己的行为树拿到一个原子动作 → ② 把动作作用到网格 → ③ 收集成 StepRecord → ④ 调 on_step 回调（可视化）。所有 agent 都成功或到达 max_steps 才停。

executor.py · 主循环（简化）
while not done and step < max_steps:
    done = _step_all_agents(env)        # 每个 agent tick + 落地动作
    record = _collect_step_record(env, step, done)
    if on_step: on_step(record, env)    # → 交给 Visualizer 渲染/打印
    step += 1

❹ visualize.py — Part 3 可视化 ●

Visualizer.on_step(record, env) 被当作回调交给 executor。每步它渲染 MiniGrid pygame 窗口 （按 fps 限速），并把每个机器人的行为树 tick 结果按 SUCCESS/RUNNING/FAILURE 上色打印。任务完成后 hold_open() 让窗口停住。渲染与执行完全解耦——关掉它执行逻辑一行都不用改。

❺ run.py — CLI 编排 ●

命令行入口，把四块按 scenario → plan → execute(on_step=viz) 顺序串起来，并处理 --smoke 预设、无头模式 SDL dummy 驱动、执行前 random.seed 等细节。详见 §运行。

❻ verify.py — 无头自检 ●

CI 风格冒烟测试：把库的海量 stdout 重定向到 devnull，只在 stderr 打心跳和 RESULT。关键是 run_with_retry(attempts=5)——因为单次只有 ~70% 成功率（见 §非确定性），靠换种子自动重试 把整体失败率压到 1% 以下。实测 10/10 全过。

② 新增一个复合宏（多步子任务）

复合宏 = 一个名字 → 一串有序原子动作，self 占位符在规划时会绑定到具体的 agent-i。 把它加进某个机器人的宏库字典即可。可用的原子动作积木：

原子动作含义
GoToInRoom(self, obj, room)走到某房间里的某物体旁
PickUp(self, obj)捡起物体
GoBtwRoom(self, r_from, r_to)跨房间移动（含随机寻路）
Toggle(self, door)开/关门
PutInRoom(self, obj, room)把手里的物体放进某房间
PutNearInRoom(self, obj, anchor, room)把物体放到某锚点物体旁

③ 换规划算法 / 单独调用某一段

因为三段解耦，你可以绕过 run.py，在自己的脚本里只用其中一段。比如对比 optimal vs basic 规划：

my_experiment.py · 直接调用各段
from app.scenario import smoke_scenario
from app.planner  import plan_behavior_trees
from app.executor import execute

scn = smoke_scenario(num_agent=2)
env = scn.build_env(render=False)

for use_optimal in (True, False):          # MAOBTP vs MABTP
    plan = plan_behavior_trees(env, scn, optimal=use_optimal)
    res  = execute(env, plan, share_belief=True, max_steps=400)
    print(f"optimal={use_optimal}: success={res.success} steps={res.steps}")
🗺️ 扩展速查 · 我想改什么 → 动哪里

换目标 / 换物体 / 换地图 → scenario.py 写新 Scenario 工厂 + 注册进 SCENARIOS。
加新多步技能 → 在某 agent 的 composite_library 字典里加一条宏。
换规划算法 → planner.py 里换 MAOBTP / MABTP，或 import CABTP（单机器人建宏）。
换协同策略 → executor.py 的 share_belief 开关 / _disable_belief_sharing。
换渲染方式 → visualize.py 的 Visualizer，签名匹配 StepCallback 即可替换。

11关于非确定性（很重要）

很多人第一次跑会困惑："为什么同一个种子，两次跑出来步数不一样？" 答案是——执行过程 本质上是随机的，而且提前播种也锁不死。有两个独立的随机源在起作用：

🔑 为什么 --seed 也锁不死？

因为规划阶段会先消耗掉不定量的随机数（搜索耗时每次不同），等轮到执行时 RNG 状态已经 跑偏了，所以"提前播种"无法固定执行路径。这是多机器人执行器的固有性质，不是规划 bug。

✅ 正确做法：自动重试，而不是找"魔法种子"

verify.py 的 run_with_retry(attempts=5) 每次用 base_seed + i 播种、 跑一次、首次成功即返回。每次重试都是独立的新轨迹，5 次里整体失败率压到 1% 以下—— 实测 10/10 全过。
如果你用 run.py --smoke（无重试），偶尔不走运就再跑一次，或调大 --max-steps 即可。

一句话总结：规划是确定的、可复现的；执行是随机的、靠重试保证可靠。地图越大、机器人越多， 步数方差越大。
